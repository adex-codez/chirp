Chirp · Engineering research

WebSocket architecture

How to open realtime connections, serve different feature needs, protect performance, and scale delivery for a mobile social app.

Research briefPrimary sourcesUpdated 29 October 2026

Chirp has a Go and Gin backend, a React Native mobile app, and Postgres as its durable store. WebSockets should add a fast delivery path while domain services and the database remain the source of truth.

Recommended start

One authenticated /ws connection per app session, bounded read/write loops, typed events, and feature-specific delivery guarantees.

01

Open the connection

Protocol factWebSocket starts with an HTTP Upgrade handshake. A successful server response switches protocols; then both sides exchange framed messages over one persistent connection. Use wss:// over TLS in production. The protocol also defines subprotocol negotiation, Origin, Ping/Pong, and the close handshake.

HTTPS requestClient sends upgrade request and access proof
AuthenticateValidate token, session, and origin policy
UpgradeAccept the handshake or return HTTP error
RegisterAttach connection to the authenticated User
ExchangeRead commands; write authorized events

RecommendationAuthenticate before upgrading. Prefer a short-lived access token in handshake headers when the shipped mobile runtime supports it. If not, mint a short-lived, single-use ticket through HTTPS and consume it at connect time. Never put long-lived credentials in a URL. Origin checks help protect browser clients but do not authenticate native apps.

Use a versioned application envelope such as chirp.v1 only where protocol compatibility needs it. The subprotocol is a version label, not an access-control mechanism. Keep a single endpoint and authorize each command and subscription independently.

02

Make connection lifecycle explicit

Represent a connection as connecting → authenticated → active → closing → closed. Register it by User and connection ID; remove it idempotently when the socket closes. A User may have multiple devices, so online state should account for more than one live connection.

  • Use Ping/Pong heartbeats and set deadlines shorter than the infrastructure’s idle timeout.
  • Reconnect with exponential backoff and jitter; refresh credentials over the existing HTTPS flow.
  • On reconnect, fetch missed durable state from the API using a cursor; deduplicate events by stable ID.
  • During shutdown, reject new upgrades, notify connected clients, drain for a bounded period, then close.

Mobile networks and app backgrounding make disconnection normal. A live connection does not prove that an event was received or processed.

03

Use one transport, different delivery rules

Keep typed commands and server-pushed events on the shared connection. Let existing domain services validate and persist changes; the socket layer handles authentication, bounded decoding, routing, and subscription authorization.

FeatureDelivery modelReconnect behavior
Chat messagesPersist first, then publish to authorized conversation members.Fetch history after the last cursor; deduplicate by message/event ID.
PresenceEphemeral per-User state with heartbeat leases and device counts.Expire stale leases; rebuild from active connections.
Typing / read stateShort-lived and conversation scoped; coalesce repeated updates.Drop under congestion; emit fresh state when useful.
NotificationsPersist unread state, then push a wake-up or update event.Fetch authoritative inbox state from HTTPS APIs.
RoomsServer-authorized subscription to a conversation or topic.Reauthorize membership on subscribe and sensitive commands.

Durable chat and notification state belongs in Postgres. Presence and typing are temporary hints. This split lets transient updates be dropped while clients recover durable state after reconnect.

04

Protect performance and slow clients

For Go, use one reader and one writer loop per connection. Producers send through a bounded outbound queue; only the writer loop calls write methods. Set message-size limits and read/write deadlines, and validate message type and rate before invoking business logic.

  • Never use an unbounded per-client queue. Drop or coalesce transient updates; disconnect slow clients that cannot keep up with durable events.
  • Batch recipient lookups and encode an event once when payloads are identical.
  • Measure before enabling compression; it trades CPU for bandwidth and may be unsuitable for mixed secret-bearing payloads.
  • Bound concurrent handshakes and connections per User, device, and IP.

Track active connections, queue depth and drops, bytes and messages per second, fanout size, handshake time, and event enqueue-to-write latency. Use measurements to set resource limits.

05

Scale fanout with clear guarantees

For one Go process, an in-memory map from User or room to connections is enough. It cannot find a User connected to another replica. Once Chirp runs multiple backend instances, add shared event fanout; connection affinity alone does not deliver events across instances.

Keep a small event-bus seam. Start in-process, then add Redis Pub/Sub for low-latency ephemeral fanout if multiple replicas need it. Redis Pub/Sub is at-most-once: disconnected subscribers miss messages. Pair it with durable Postgres state and client reconciliation. Use a durable stream or queue when replay or stronger delivery guarantees matter.

Postgres LISTEN/NOTIFY can wake up other processes, but it is not a message history. For events that must be published whenever a database change commits, a transactional outbox can store the event alongside the domain update and retry publishing asynchronously.

06

Secure each handshake and message

  • Use TLS and an explicit browser Origin allowlist; treat Origin as a browser defense, never as identity.
  • Authenticate at handshake and authorize every command and room subscription.
  • Close or revalidate connections when the short-lived access token expires or the session is revoked.
  • Apply message-size limits, schema allowlists, rate limits, and conversation membership checks.
  • Do not log tokens or message bodies. Log lifecycle, close reasons, authorization failures, malformed input, queue drops, and abnormal disconnects.
07

Recommended first architecture

  1. Add authenticated /ws route in Gin. Validate access token and applicable Origin policy before upgrade.
  2. Use a maintained Go WebSocket implementation with one read loop and one write loop per connection, bounded queues, heartbeat deadlines, and cleanup.
  3. Define a typed, versioned event envelope and server-authorized subscriptions. Keep domain writes in services.
  4. Persist chat and notification state before publishing. Reconcile on reconnect from Postgres-backed APIs.
  5. Start with in-process routing. Add Redis Pub/Sub when replicas need ephemeral cross-node fanout; add a durable outbox or stream when delivery requirements justify it.

TradeoffThis keeps the first release operationally small while supporting several realtime features. In-process routing is process-local; a broker later adds cross-node delivery along with duplicate, loss, and failure modes that need explicit handling.
